## 一、当前状态一页速览

**入库链路**：`parse_file`（txt/md/csv/pdf/docx）→ `sanitize`（清洗+PII 脱敏）→ `chunk_text`（句界切分 500/128）→ `embed` → `vector_store.add`（doc_id + tenant_id 元数据）→ SQLite 登记

**检索链路**：查询 → 向量召回（top_k×3 扩容，上限 50）＋ BM25 召回（租户+语料指纹缓存）→ 租户过滤 → RRF 融合（k=60，权重 向量 0.4 / BM25 0.6）→ 可选重排序 → 返回（含来源溯源）

**当前实测基准（2026-09-25，`python scripts/eval_rag.py --topk 3`）**：
- 语料 **1012 文档 / 1247 分块**（750 真实商品 + 259 领域文章 + 3 原示例，节点 15）
- 评测集 52 条：**Recall@3 = 45/52 = 86.5%**、Recall@5 = 48/52、**MRR@3 = 0.824**
- 热查询 **1.6 ms**（memory 向量库 + 缓存全热）
- 注：3 篇示例 / 4 分块时代的旧基准为 Recall@3 = 52/52 全命中、MRR@3 = 0.942、耗时 <1 ms（2026-09-17）——已被 1012 篇真实语料新基准取代，仅作历史对照，不得再对外引用。

### 节点 1 ｜ 2026-08-27 ｜ v0.1：入库链路首次打通

- **做了什么**：`parse_file` 支持 txt/md/csv（utf-8 解码）、pdf（pypdf）、docx（python-docx），不支持类型显式报错；`sanitize` 清洗 + PII 脱敏；`chunk_text` 按段落→句子→硬切三级切分，默认 500 字符 / 重叠 128。
- **验证**：冒烟测试 6 项通过；导入 3 篇示例文档切出 4 个分块；检索正确命中。

### 节点 2 ｜ 2026-08-27 ｜ 踩坑修复：memory 向量库跨进程丢数据

- **现象**：memory 向量库纯内存实现，进程重启后已入库文档全部丢失，检索为空。
- **修复**：`add`/`delete` 后自动 JSON 持久化到 `data/index/vector_store.json`，构造时 `_load()` 回载。
- **影响深远**：这个修复后来让 `eval_rag.py` 可以单进程直跑（见节点 12 的澄清）。
- **证据**：`backend/app/core/vector_store/memory.py`（`_save`/`_load`）、`backend/app/core/vector_store/factory.py`（`MEMORY_INDEX_PATH`）。

### 节点 3 ｜ 2026-08-28 ｜ 第一轮：BM25 索引缓存 + 写路径失效

- **做了什么**：BM25 索引按「(租户, 语料指纹)」缓存（指纹 = 文档 id 元组），避免每次检索全量重建；知识库增删后由 knowledge 服务调用 `invalidate_bm25_cache()` 强制失效。防御性设计：缓存只保留最新一份，避免并发增删导致堆积。
- **证据**：`backend/app/services/rag/retriever.py`（`_bm25_cache`、`_get_bm25`、`invalidate_bm25_cache`）、`backend/app/services/knowledge.py`（增删末尾调用失效）、`docs/项目文档.md` §7 第一轮。

### 节点 4 ｜ 2026-08-29 ｜ 第二轮：向量库归一化矩阵惰性缓存

- **做了什么**：memory 向量库把逐条余弦相似度改为「行归一化矩阵 × 查询向量」一次矩阵运算；矩阵惰性构建（`_norm_matrix`），add/delete/加载后由 `_invalidate_matrix()` 失效。
- **效果**：检索从 O(n) Python 循环变为 numpy 向量化，是后续「<1ms 检索」的基础。
- **证据**：`backend/app/core/vector_store/memory.py`（`_get_norm_matrix`、`search`）。

### 节点 5 ｜ 2026-08-29 ｜ 第三轮：评测基建（先有尺子再调优）

- **做了什么**：新增 `scripts/eval_rag.py`，对评测集逐条检索，计算 **Recall@K + MRR + 平均耗时**，并输出逐条命中排名与未命中样例；初始评测集 20 条（`data/eval/rag_eval.json`）。命中判定口径：`is_hit` = 结果文本包含评测案例的全部 `must` 关键词。
- ** why**：调权重/换模型前先固化评测口径，避免「凭感觉调优」。
- **证据**：`backend/scripts/eval_rag.py`、`backend/data/eval/rag_eval.json`、`docs/项目文档.md` §7 第三轮。

### 节点 6 ｜ 2026-08-29 ｜ 第三轮：重排序双实现（默认零依赖，可选真模型）

## 三、踩坑与修复对照表

| # | 坑 | 现象 | 修复 | 预防约定 |
|---|---|---|---|---|
| 1 | memory 向量库不持久化 | 进程重启后知识全丢，检索为空 | add/delete 后自动 JSON 持久化（`vector_store.json`） | 任何存储实现必须回答「重启后数据在哪」 |
| 2 | BM25 每次检索全量重建 | 大语料下检索变慢 | 按（租户, 语料指纹）缓存 + 写路径失效 | 缓存必须有明确失效时机，不能只靠 TTL |
| 3 | 混合权重文档写反 | 面试文档写「向量 0.6/BM25 0.4」，与运行时相反 | 统一为配置口径：向量 0.4 / BM25 0.6 | 形参默认值 ≠ 生效值，写文档以 config 为准 |
| 4 | 以为评测需同进程入库 | 不敢单独跑评测脚本 | 实测澄清：JSON 持久化使独立脚本可直跑 | 结论先实测再下，不凭直觉推断 |
| 5 | 历史向量无 tenant_id | 升级后旧数据检索被过滤光 | `_tenant_filter` 把无标记数据视为 default 租户 | 加列必须配 server_default + 兼容读 |
| 6 | 同名文档重复上传导致知识膨胀 | 同一篇文档占双份向量 | 同名替换语义：先删旧（按 doc_id 精确匹配）再入库 | 删除必须精确到 doc_id，filename 只作历史回退 |
| 7 | rerank 内部打分泄漏 | `_rerank_score` 混进 API 响应 | 返回前统一 `pop` | 中间计算字段不外泄，出接口前清理 |

| 混合权重 | 向量 0.4 / BM25 0.6（配置生效值） | `config.py HYBRID_WEIGHT_*` |
| 重排序 | heuristic 默认；cross_encoder 可选+失败回退；默认关闭 | `config.py RERANK_PROVIDER`、`ENABLE_RERANK` |
| BM25 参数 | k1=1.5, b=0.75，纯 Python 实现 | `rag/bm25.py` |
| 向量库 | memory（JSON 持久化）/ chroma 可切换 | `core/vector_store/` |
| 租户隔离 | 元数据 tenant_id + 检索后过滤 + doc_id 精确删除 | `rag/retriever.py`、`services/knowledge.py` |
| 支持格式 | txt / md / csv / pdf / docx | `services/knowledge.py SUPPORTED_EXT` |
