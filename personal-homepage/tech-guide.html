Embedding 把文本映射为稠密向量、语义相近则向量相近，面试常问选型三维度：中文效果、向量维度、推理成本。

BM25 是基于词频与逆文档频率的稀疏检索，面试必问与向量检索的互补性：专有名词、型号、编号类查询它显著更强。

向量检索深入 →

向量检索依赖 ANN 索引（HNSW / IVF），面试常问召回率与速度的权衡，以及余弦相似度与内积该怎么选。

RRF 融合深入 →

RRF 用 1/(k+rank) 按排名融合多路检索结果，面试亮点：不需要调各路分数的权重、对异构检索器天然鲁棒。

Rerank 用交叉编码器对粗排 Top-N 逐对精排，面试必问为什么不直接全库交叉编码：算力开销完全不可接受。

Query Rewrite 解决多轮指代与口语化提问，面试可举例：把「它怎么配置」用 LLM 改写成含上下文的完整独立查询。

ChromaDB深入 →

Chroma 是轻量嵌入式向量库，面试常问与 Milvus / PgVector 的边界：十万级以下开发期首选，生产大规模换分布式方案。

1 RAG 全链路

Retrieval-Augmented Generation，检索增强生成

是什么

RAG 就是「先查资料，再让大模型回答」。它解决大模型的两个硬伤：知识过时（训练数据有截止日期）和幻觉（一本正经编答案）。做法是把企业私有文档存进向量库，用户提问时先检索最相关的片段，连同问题一起喂给大模型，让模型「基于证据」作答，并给出出处。

核心链路（你项目里就是这条）

  • 文档解析：PDF / Word / Markdown / Excel 用 PyMuPDF、python-docx 等解析成纯文本。
  • 切片 Chunking：长文切成小段（常用 RecursiveCharacterTextSplitter，按标题/段落递归切）。
  • Embedding：每段文本转成向量（一串数字），语义相近的文本向量也相近。
  • 入库：向量存进向量库（ChromaDB / Milvus / PgVector）。
  • 检索：问题也转向量，找最相似的若干段（语义检索）+ 关键词检索（BM25）融合。
  • 重排：初步结果用 Rerank 模型精排，挑最相关的。
  • 生成：拼接「问题 + 检索片段」给 LLM，SSE 流式输出答案，附带来源 doc_id。
你在「企业智能知识中枢 · RAG 底座」里把所有环节都自研了一遍，并实现了按 doc_id 增量更新（删旧块→写新块），新 SOP 分钟级生效——这就是简历里的核心技术亮点。
为什么不用微调（Fine-tuning）而用 RAG？
知识库每周更新约 30%，微调要把新数据重新训练、周期长成本高，且无法给出答案出处（合规审计要求原文可溯源）。RAG 改文档即生效、天生可溯源，更适合「知识频繁变动 + 要可解释」的企业场景。结论：优先 RAG，微调只用在垂直风格/格式适配上。
Chunk 切太大或太小有什么问题？怎么定？
太大→一段塞太多噪音，检索精度下降、浪费 token；太小→语义被切碎，单块信息不全。经验值 300~800 字 / 块，重叠（overlap）10%~20% 防止语义在边界被切断；专业文档按标题结构切更稳。
怎么衡量 RAG 效果好不好？
分阶段看：检索层用「召回率 / 命中率」；生成层用「有答案率、忠实度（是否编造）、相关性」。工程上靠「坏例驱动」——收集答错的问题，定位是检索没召回还是生成跑偏，针对性调优，而不是单点调一个大指标。

2 混合检索：BM25 + 向量 + RRF

Hybrid Retrieval，用两种互补的检索拼在一起

两种检索的差别

  • 向量检索（语义）：靠 Embedding 算相似度，能理解「同义词 / 换个说法」。但专有名词、型号、缩写容易翻车（比如 "L/C" 和 "信用证" 不一定向量接近）。
  • BM25（关键词）：经典信息检索算法，按词频和逆文档频率算相关，精确匹配强——"FOB""CIF""L/C" 这类术语它一抓一个准，但理解不了语义。

RRF 怎么融合

RRF = Σ 1/(k + rank_i)，k 通常取 60。两个检索各自排好名，把每个文档在两份榜单里的排名按这个公式打分再相加，得到融合排名。好处是不依赖分数绝对值（向量得分和 BM25 得分量纲不同，不能直接加），只看相对名次，简单又稳。

你项目里是自研 HybridRetriever 同时跑 Chroma 向量召回和 BM25 稀疏召回，RRF 融合后再接轻量精排器二次重排，专门解决「专业术语场景纯语义检索命中不稳」。
为什么不能直接把向量得分和 BM25 得分加一起？
两者分数分布不同（向量是余弦 0~1，BM25 可能很大），直接加权相加会被某一方的量纲主导，需要归一化。RRF 只用「排名」不看分数大小，绕开了量纲问题。
RRF 的 k 怎么选？影响大吗？
k 控制「低排名项衰减多快」。k 越大，排名靠后的项贡献越大，融合越平滑；常用 60。对结果影响不算敏感，调参收益远小于把两路召回本身做对。

3 重排序 Rerank

Retrieval 之后再做一次精排，提升 top-k 质量

是什么

召回阶段（向量+BM25）追求「快、广」，可能召回几十条；Rerank 阶段用更大的交叉编码器（Cross-Encoder）把「问题 + 每个候选片段」成对送入模型，判断真正的语义相关度，把 top-k（比如 3~5 条）留给生成环节。Bi-Encoder（Embedding）快但粗，Cross-Encoder 慢但准，所以先召回后重排是标准搭配。

你的「混合检索 + 二次重排」亮点是：RRF 融合后接一个轻量精排器，按字符重合度再筛一遍，兼顾「精确关键词命中」和「语义相关性」。
为什么不能一开始就用 Rerank 模型直接检索？
Cross-Encoder 是对「query 和 doc 两两组合」算分，候选有上万条时组合爆炸、太慢。所以检索用便宜的 Bi-Encoder 先缩到几十条，再上 Cross-Encoder 精排，是性能与效果的折中。

4 Multi-Agent 与 LangGraph

多智能体编排：让多个 Agent 分工协作完成复杂任务

核心概念

  • Agent：能「感知→规划→调工具→执行」的循环体，本质是 LLM + 工具 + 记忆。
  • 意图路由：先判断用户想干嘛（问答 / 规划 / 管理 / 应急），再分发给对应 Agent。
  • Supervisor 调度：一个「主管」Agent 决定下一步交给哪个子 Agent，类似项目经理。
  • StateGraph（LangGraph）：用「状态图」编排 Agent，节点 = 步骤，边 = 流转，共享 State 在节点间传递意图和结果，支持条件分支和长期状态管理。

你的实践

智慧出行里用三层 FastAPI 微服务 + LangGraph StateGraph 意图路由，编排中心做调度、规划引擎生成行程、感知引擎监控实时数据。RAG 底座里用 route→act 两节点：规则分类器判断「纯问答 or 行动办理」，注册 query_knowledge / launch_workflow / list_workflows 三类工具，把「查知识」和「办业务」串成闭环（查完即办）。

LangChain 与 LangGraph 的选型边界（你的收获原话）：核心看两点——是否要复杂条件分支、是否依赖长期状态管理。简单链路用 Chain 即可，有状态流转才上 Graph。
LangChain 和 LangGraph 到底什么关系？什么时候用哪个？
LangChain 是组件库（链、检索器、工具），适合线性 Pipeline；LangGraph 在其之上用图来编排，适合有「循环 / 分支 / 多轮状态」的 Agent。一句话：要状态机和可控流转就 LangGraph。
Agent 怎么避免「乱调工具」或陷入死循环？
① 工具定义清楚输入输出和边界；② 用状态图显式约束流转（只能走允许的边）；③ 设最大步数 / 超时护栏；④ 关键动作（如发审批、写库）加确认或权限校验，不能让 Agent 无脑执行。
你项目里「查完即办」的闭环是怎么实现的？
意图分类器判定是「行动类」后，进入 act 节点，调用注册好的业务工具（launch_workflow 等），工具执行结果回写 State，再决定下一步。需要人工审批的环节（如差旅超标）插入审批门禁，未通过不生效。

5 大模型接入与多模型热切换

LLMManager：一个接口接 DeepSeek / Qwen / 混元 / GLM / Moonshot

是什么

不同厂商的大模型 API 格式各异。你封装了一层 LLMManager，内部维护「多服务商注册表」，统一成 OpenAI 兼容接口。业务代码只调一个方法，运行时改配置即可切换模型，业务零改动；配置持久化，重启自动恢复。

关键能力

  • 热切换：线上根据效果/成本/可用性随时换模型，不重启服务。
  • 降级：无 API Key 时走内置规则引擎 + 哈希向量兜底，全链路离线可验证。
  • 私有化：DeepSeek / Qwen 用 vLLM 本地部署对外提供推理服务。
OpenAI 兼容接口封装有什么好处？
市面上一大半国产模型（DeepSeek、通义、Moonshot、GLM、混元）都提供 OpenAI 格式兼容端点。统一成这一套后，换模型只改 base_url 和 api_key，调用代码不变，极大降低耦合。
多模型热切换在生产上要注意什么？
① 不同模型输出格式/能力不一，要测对齐；② 切换有延迟和失败率，需熔断+降级；③ Token 计费和限速不同，成本看板要区分；④ 配置变更要灰度，别全量一刀切。

6 Embedding 选型

中文 RAG 用 BAAI/bge-large-zh-v1.5（1024 维）

是什么

Embedding 模型把文本变成向量，是语义检索的地基。选错模型，后面再怎么调重排都救不回来。

你的选型结论：中文场景锁定 BAAI/bge-large-zh-v1.5（1024 维），弃用 OpenAI ada 和 M3E。理由——bge 系列中文榜单常年靠前，且支持「指令式检索」（给 query 加前缀提升召回）；ada 中文弱、M3E 效果已被 bge 超越。支持「本地私有化 / OpenAI 兼容 API / 关键词降级」三后端可插拔，失败自动熔断。
维度（1024）对检索有什么影响？
维度越高通常表达能力越强，但存储和检索开销也大。1024 是效果与成本的平衡点。关键是检索时和入库时要用同一个模型，否则向量空间不一致，检索全废。
为什么强调「本地私有化」Embedding？
企业文档涉敏，走外部 API 有合规风险且依赖网络。本地部署 bge 既能离线跑，又避免数据出境；同时保留云端 API 作为可插拔备选。

7 SSE 流式输出与异步并发

FastAPI + SSE，让答案「边想边出」

是什么

SSE（Server-Sent Events）是服务端向浏览器单向推流的协议。大模型生成慢，如果等全部生成完再返回，用户要干等很久；用 SSE 逐 token 推送，前端打字机式渲染，首字到达即可见，体验好很多。你项目里问答首字响应优化到 1.3 秒。

你踩过的坑（重点，面试常问）

  • 阻塞事件循环：async 路由里同步调 LLM，会卡死整个服务。→ 线程池化（run_in_executor）。
  • 并发串单：生成器写成全局单例，多用户请求互相覆盖配置、"串单"。→ 每请求独立实例。
  • 异常污染 JSON：LLM 报错文本混进行程 JSON。→ 独立 error 帧协议 + 重试保护。
  • 非原子写：JSON 文件并发写入损坏。→ 临时文件 + rename 原子替换 + 线程锁。
这些「线上 bug 修复」是简历硬货：把「服务卡死 / 串单 / 数据损坏」的根因和修复说清楚，最能体现工程能力，比讲模型原理更打动面试官。
SSE 和 WebSocket 有什么区别？为什么用 SSE？
SSE 是服务端→客户端的单向流，基于 HTTP、实现简单、自动重连；WebSocket 是全双工双向。问答/行程生成只需要服务端推，不需要客户端频繁发，SSE 刚好够用且更轻。
FastAPI 里 async 和 sync 路由混用要注意什么？
async 路由里不能写阻塞 IO（如同步 requests、同步 LLM 调用），否则占住事件循环。阻塞操作要用线程池（run_in_executor）或换成异步 SDK。你的「线程池化」就是为此。

8 记忆与状态管理

多轮对话 / Agent 状态，靠 Memory + Redis

是什么

  • 会话记忆：用 ConversationBufferMemory 按 session_id 存最近 N 轮对话，检索时拼上下文，支持指代消解（"它"指前文）。为防止长会话记忆膨胀，按轮数裁剪窗口。
  • Agent 状态缓存：Redis 存 Agent 运行态、会话历史，跨请求复用、支持高并发。
长对话怎么控制 token 成本？
① 只保留最近 N 轮（滑动窗口）；② 更早的对话做摘要压缩成一段；③ 或用向量检索只召回与当前问题相关的历史片段，而不是全量塞进去。
为什么 Agent 状态放 Redis 而不是内存变量？
多进程 / 多实例部署下，进程内存不共享，用户第二次请求可能落到另一个实例，状态就丢了。Redis 是共享、可持久化的中心存储，且支持过期和并发安全。

9 安全与鉴权

JWT / 脱敏 / 越权防护（IDOR）

你做了什么

  • JWT 认证：PBKDF2 + HS256，零第三方依赖（自己实现，不引库），多角色权限控制，注册防自助提权。
  • 收窄后门：dev 万能 key 仅开发环境生效，生产关掉。
  • 越权防护（IDOR）：行程生成后校验属主，防 A 用户改 B 用户的行程。
  • Prompt 脱敏 & 合规：PII 脱敏（解析阶段清掉身份证/手机号等）、内容合规校验、敏感信息过滤。
HS256 和 RS256 的 JWT 有什么区别？你为什么用 HS256？
HS256 用同一个密钥签名+验签（对称），RS256 用私钥签、公钥验（非对称，适合多服务）。你项目是单体/少服务，HS256 足够且实现简单，所以零依赖自实现。多服务分发的场景才更值得上 RS256。
什么是 IDOR？怎么修？
Insecure Direct Object Reference：用户改 URL/参数里的 id 就能访问别人的数据。修法是每个涉及资源的接口都校验「当前用户是否拥有该资源」，而不是只靠登录态。
Prompt 注入怎么防？
把「系统指令」和「用户输入」严格分离、用分隔符包裹用户输入；对会触发工具调用的输入做权限二次确认；对外显内容做敏感词/合规过滤；不可信文档进知识库前先做清洗脱敏。

10 可观测性

Token 统计 / 监控 / 日志 / 链路追踪

是什么

AI 应用出问题时很难定位——是检索没召回？模型抽风？还是接口超时？所以需要三件套：

  • 指标（Metrics）：接入 Prometheus，看 QPS、首字延迟、Token 用量（支撑成本看板）。
  • 日志（Logs）：结构化 JSON 日志，便于检索；Token 用量接 LLM 真实 usage。
  • 链路追踪（Tracing）：一次请求穿过路由→检索→重排→生成，全链路打点，定位瓶颈。
你的原话：「企业级 AI 落地，工程厚度比模型效果更关键，PoC 到生产差的往往不是算法而是稳定性与可观测性。」这句话建议背下来，面试官很吃这套认知。
怎么评估一次 RAG 回答的「成本」？
用 LLM 返回的 usage 字段（prompt_tokens + completion_tokens），乘单价得单次成本；按会话/按模型聚合做成本看板；结合命中率看「每有效回答的花费」，指导是否要换小模型或缩短上下文。

11 部署与运维

Docker Compose / Nginx / 跨平台一键启动

你做了什么

  • 容器化：多服务（前端 / 后端 / 中间件）用 Docker Compose 编排，一条命令起全套。
  • 跨平台：Windows / POSIX 一键启动器，外贸平台用 launcher 同时拉起前后端。
  • 反向代理：Nginx 做 HTTPS、静态资源、端口转发。
  • 离线降级：任何依赖缺失（LLM / 向量 / 感知数据）都能 Mock 兜底，功能链路不断。
为什么需要「全链路降级」？
企业内网常缺外部 API Key 或网络受限，但还要能演示和跑通。降级让「没模型走模板、没向量走关键词、没实时数据走 Mock」，保证任何时候系统都能用、能讲清楚，不至于 demo 翻车。
Docker 和直接跑 Python 脚本比，优势在哪？
环境一致（开发=测试=生产）、依赖隔离、一键扩缩、便于 CI/CD 和标准运维。对多服务系统，Compose 把启动顺序和网络都管起来，省去手动配环境。

12 模型微调 LoRA

用 LoRA 提升模型在垂直业务场景的适配

是什么

全量微调要改全部参数，贵且易灾难性遗忘。LoRA（Low-Rank Adaptation）只在 Transformer 层里插入很小的「低秩矩阵」做训练，原模型冻结、只训新增的少量参数，显存省、训练快、还能多个 LoRA 热插拔切换。

你在领铄的经历里提到：完成 DeepSeek / Qwen 私有化部署（vLLM 推理），并用 LoRA 微调提升垂直业务场景适配。这是「部署 + 微调」都碰过，比只调 API 的候选人更有深度。
LoRA 相比全量微调的优势？
① 训练参数量极少（常 <1%），显存和算力需求大降；② 原模型不变，一个基座可挂多个 LoRA 适配不同任务；③ 不易灾难性遗忘；④ 权重小、便于分发和热切换。
什么场景值得微调，什么场景 RAG 就够了？
要「改模型的说话方式 / 特定格式输出 / 领域风格」→ 微调或 LoRA；要「注入最新/私有事实并要可溯源」→ RAG。你简历的取向是：RAG 做主、LoRA 做垂直适配补充，不依赖微调解决知识更新。
